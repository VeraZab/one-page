If you're like me, you use both Claude Code and Codex. You drift between them over time as they each get better — sometimes one pulls ahead and you want to switch it up, or you let one review the other's work. And you hit the same little annoyance: you don't want to set things up twice. You add a skill or tweak your instructions in one, and you just want the other to have it too.

I went looking for how far you can actually take that. The frank answer: three things sync cleanly — your **instructions**, your **skills**, and your **MCP servers**. The first two are just shared files and symlinks; MCP needs a tiny generator. No framework, no sync daemon. For a lot of setups, that's genuinely enough. The rest — hooks, permissions, subagents, plugins — stays native to each tool, and I'll be straight about that too.

## Start here: one instructions file for both

This is the single highest-leverage thing you can do, and it takes a minute.

Claude Code reads `CLAUDE.md`; Codex reads `AGENTS.md`. Same idea, different name. So if you're tired of keeping two copies in sync, put the real content in **`AGENTS.md`** and let Claude pull it in:

```md
<!-- CLAUDE.md -->
@AGENTS.md
```

Claude Code expands `@`-path imports, so it reads your `AGENTS.md`; Codex reads it natively. Now you edit one file. Prefer a symlink? That works too:

```bash
ln -s AGENTS.md CLAUDE.md
```

And you can do the same for your *personal* defaults, machine-wide:

```
~/.claude/CLAUDE.md  ->  ~/agent-config/AGENTS.md
~/.codex/AGENTS.md   ->  ~/agent-config/AGENTS.md
```

If most of your frustration is "the two agents don't behave the same," this alone fixes it — your context and rules live in one place now.

## Then: your skills, shared as-is

Skills feel like they'd be the hard part. They're not, and this surprised me when I dug in: Claude Code and Codex implement the **same `SKILL.md` spec** — YAML frontmatter with `name` and `description`, then a markdown body. Only the folders differ. Claude reads `.claude/skills/`; Codex reads `.agents/skills/`.

So if you already have skills written for one, point the other at the same folder. Make `.agents/skills/` your source of truth (it's Codex's native location anyway) and symlink Claude at it:

```bash
ln -s ../.agents/skills .claude/skills   # Claude now reads the same folder
```

Write a skill once, both agents use it. And you're not fighting the tools to do this — Codex's own docs say it "supports symlinked skill folders and follows the symlink target when scanning." (It reads `~/.agents/skills` at the user level too.)

Two things to know so you don't get surprised:

- **You trigger them differently.** Claude uses `/skill-name`, Codex uses `$skill-name`. Same skill, different keystroke.
- **Keep the frontmatter plain.** Stick to `name`, `description`, and your instructions. Tool-specific extras don't travel — Claude's `argument-hint` / `disable-model-invocation`, Codex's `agents/openai.yaml` sidecar. Keep the core clean and the same file runs in both.

## What mine looks like

If it helps to see it wired up, my dotfiles do exactly this at the user level — one `AGENTS.md` symlinked into both agents, with Claude-only settings kept separate:

```
agent-config/
├── AGENTS.md            ← canonical, symlinked to both agents
├── mcp/
│   ├── servers.json     ← canonical MCP list
│   └── sync-mcp.mjs     ← generates both formats
├── claude/
│   ├── settings.json    ← Claude-only (permissions, plugins)
│   └── statusline.sh
└── bootstrap.sh         ← recreates the symlinks on any machine
```

It's on GitHub: [github.com/VeraZab/agent-config](https://github.com/VeraZab/agent-config). `bootstrap.sh` is a dozen lines of `ln -s`. That's the whole trick — version-controlled files plus symlinks, reproducible with one command.

If that's all you need, you can stop here — plenty of setups won't need more. If you lean on MCP servers or custom tooling, keep going.

## MCP: one list, both formats

MCP is the one piece you can't just symlink, because the two tools want different file formats. Claude reads a JSON `mcpServers` object (in `.mcp.json`); Codex reads `[mcp_servers.*]` tables (in `~/.codex/config.toml`). Same servers, different syntax.

So keep one list and generate both. In my repo that's a `servers.json`:

```json
{
  "mcpServers": {
    "context7": {
      "command": "npx",
      "args": ["-y", "@upstash/context7-mcp"]
    }
  }
}
```

and a ~30-line script that turns it into each tool's format:

```bash
node mcp/sync-mcp.mjs
#  -> mcp/claude.mcp.json   { "mcpServers": { ... } }
#  -> mcp/codex.toml        [mcp_servers.context7] command = "npx" ...
```

Point Claude at the JSON (symlink a project `.mcp.json` to it), drop the TOML block into Codex's `config.toml`, and both agents have the same servers. Edit the list, rerun, done. Two things worth keeping in mind:

- **Keep secrets out of the source.** Reference them as `${ENV_VAR}` and let each tool resolve them at runtime — don't bake tokens into `servers.json`.
- **Make failures loud.** You want a bad sync to be obvious and fixable by rerunning the generator, not one agent quietly running stale config.

The generator and canonical list are in the same repo: [mcp/ in agent-config](https://github.com/VeraZab/agent-config/tree/main/mcp).

## The part that stays custom

A few things genuinely don't port, and it's better to know that up front than to discover it when an agent silently misbehaves. Leave these native to each tool:

| If you use... | Expect to keep it per-tool |
|---|---|
| Slash commands | Claude's `.claude/commands/` vs Codex's prompts (now folding into skills) — adapt |
| Subagents | Share the definition where supported, native adapter otherwise |
| Hooks | Different runtime models — only sync behavior that's genuinely compatible |
| Permissions | Platform security controls — don't weaken them to force parity |
| Plugins | Claude-specific; share the skill *inside* the plugin, not the plugin |

And if you'd rather not hand-roll the harder parts, a handful of community projects try to automate this. Check their maintenance and actually test them before you depend on one — this space moves fast and advertised features don't always hold:

- [agent-config-sync](https://github.com/B0llerwagen/agent-config-sync) — Claude→Codex sync of skills, MCP, permissions.
- [ai-config-sync-manager](https://github.com/slash9494/ai-config-sync-manager) — bidirectional Claude/Codex sync.
- [ai-agent-config](https://github.com/casoon/ai-agent-config) — unified config via symlinks and generated adapters.
- [universal-agent-skills](https://github.com/26zl/universal-agent-skills) — portable skills across ecosystems.
- [openai/skills `migrate-to-codex`](https://github.com/openai/skills/tree/main/skills/.curated/migrate-to-codex) — official tooling for an initial conversion.

## If you take one thing from this

One shared layer for what you *tell* your agents, two native runtimes for how they *run*. Instructions and skills share cleanly and cover most of the value; MCP needs a tiny generator; permissions and hooks stay put. Reach for symlinks and a short script before any framework. You get to switch between Claude Code and Codex freely, without maintaining two of everything.
